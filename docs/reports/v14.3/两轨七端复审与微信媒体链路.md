# 两轨七端复审与微信媒体链路

本轮对应 `darwin-tun-r1`。个人版和公开版各检查主版与纯 IPv4 的七份入口，共 28 份。每套入口的验证结果绑定实际 SHA-256。

| 客户端 | 本轮复审 |
| --- | --- |
| Windows FlClash | 规则、分组、纯 IPv4、严格路由意图及 App 二次合并边界。用原装 FlClash 核心和 QuickJS 复核合成媒体路径。 |
| Android FlClash / Mihomo | 缺省 TUN 输入、provider、地址族和规则回归。Android VpnService 接管待实机验收。 |
| macOS FlClash | 四种模式交给 Darwin 核心生成自动路由，从旧显式默认路由升级保持幂等。Mac TUN 开关、重载和真实流量待实机验收。 |
| Windows Clash Verge Rev | 配置返回、TUN 字段归属、策略和网络模式回归。App 二次合并须以最终配置验收。 |
| iOS Clash Mi | 对象返回和序列化输入、NetworkExtension 配置、业务策略与兼容模式回归。JavaScriptCore 和设备待验收。 |

## 微信媒体

已审核的媒体主机按「国内网站」选择 DNS、TCP 和 UDP 出口。此组默认 DIRECT，手动选择代理时继续跟组。无域名公网 UDP、通用 STUN 和共享基础设施保留现有防护。项目使用可离线核对的域名策略，整个微信进程强制 DIRECT 会绕过上述组选择。 [现行分流合同](../../需求.md) · [旧版覆盖修复](云端规则审核与离线修复.md)

两套源码共 48 种 Mihomo 配置用 Windows 原装核心关闭 TUN 做隔离回环。先查询 `szfile.weixin.qq.com` 的 Fake-IP，再用该地址建立合成 HTTP 连接。每个模式的首个连接均使用选定的国内 DNS 上游并收到回环响应。上游替换成回环桩，因此耗时只用于验证本地路径，真实微信上传和公网 DNS 另行验收。 [合成媒体链路回执](../../../releases/v14.3/validation/domestic-resilience/darwin-tun-media-path.json)

出现实际发图延迟时，记录点击发送的时间、图片大小、目的域名或 IP、地址族、命中策略和出口。先区分 TUN 接管、首次建连和应用传输，再决定是否对已确认的精确域名做真实解析或嗅探对照。 [macOS FlClash 故障小本子](../../guides/macOS-FlClash故障小本子.md) · [Mihomo DNS 文档](https://wiki.metacubex.one/config/dns/#fake-ip-filter) · [Mihomo 嗅探文档](https://wiki.metacubex.one/config/sniff/)
