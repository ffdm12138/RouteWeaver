## 对当前代码的实际判断

我们已经有关键规则内嵌、完整来源固定、跨平台生成、依赖/循环检查、幂等、provider 处理、个人例外隔离与有界核心回放。这些功能不能为了文件短而删掉。当前 JS 大约 120 KiB，包含关键分类表和校验逻辑；代码长度也不能解释日志里的秒级拨号退避。

最需要整理的是构建链：`build-balanced.cjs` 仍从冻结 V14.2 源码中多次按文本锚点替换，再附加平台和网络适配。它有断言保护，能阻止静默改错；长期追加时仍不如“共享模块 + 明确阶段”易读。Mac 和兼容入口已经复用基础产物，可作为迁移起点。冻结基线继续只读。

| 优先级 | 改进 | 验收方式与当前状态 |

| P0 | 将无域名 IPv6 拨号等待放到核心，保留分流合同 | 已完成[隔离原型](无域名IPv6与转圈等待研究.md)，不是在脚本继续叠微信/IPv6 地址补丁；客户端集成待做 |

| P1 | 增加真实 JS 引擎对照，统一合成订阅与异常输入矩阵 | 参考 QuickJS 对照思路，单独证明 FlClash/Android 语言兼容；Clash Mi 的 JavaScriptCore 和对象桥仍各自验收。当前 Node 检查不能冒充这些结果 |
| P1 | 统一平台能力表和诊断快照，减少散落平台判断与每次手写分析 | 应记录客户端/核心版本、接管方式、最终 DNS/TUN/嗅探值及源哈希，输出脱敏差异；不收集真实订阅/密码，不自动重配客户端。当前为设计项 |
| P2 | 分离稳定需求、生成器回执和不断变化的用户观察 | 用户新日志放观察记录，减少仅改状态文字就刷新多层源码绑定；保持旧证据的来源和失败结果。尚未更改既有合同绑定方式 |

“更干净”指可读的共用源码、明确边界和可解释的产物，而不是压缩成一行、删掉防护或增加开关数量。本轮已改进研究重建工具，使其区分完整仓库和独立审核包，并提供不编译/不联网的固定源补丁检查；生产导入文件保持原字节。

## 当前不采用的默认值

- 关闭严格路由、全局关闭核心 IPv6，无法满足现有接管与远端 IPv6 要求。
- 自动测速/故障切换和自动 DIRECT 回落会改变两个公共组的手动选择语义。
- 将全部 CN IP 的 UDP 直连、将 STUN 豁免当作防泄漏、把微信大域名全面排除嗅探，均不能替代当前规则边界。
- 浮动规则分支、统一调 MTU/保活/并发、复制大量 DNS 例外，不能在没有对照时称为稳定性修复。并发拨号也不能为单个无域名 IPv6 目标产生 IPv4 地址。
- 共用源码项目对 HTTP/TLS 端口采用互斥范围值得检查，但我们目前在 v1.19.31 已验证重叠端口能尝试多个协议。未读出用户实际核心版本前，不直接删除 8443 的某种识别能力；补支持矩阵和分片/服务器先发反例更合适。

本次没有找到一个可直接替代当前合同、且已证明解决任意无域名 IPv6 回退的纯覆写方案。四套候选均未在本次审查中验证出“持续物理出口探测 + 任意 IPv6 到可靠 IPv4 映射 + 原出口不变”的完整实现；不是宣称所有开源项目都做不到。当前根因研究和设备验收继续独立推进。
