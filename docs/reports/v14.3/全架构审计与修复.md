## 一、Cloudflare 故障：实际隔离而不是猜测

用户 HAR 的失败是 `1.1.1.1:443` 请求连接关闭，不能仅凭状态 0 判断为 CORS、IP 风控或服务器返回了 403。域名访问 `www.cloudflare.com` 和 Turnstile 成功，也不能证明 IP 字面量访问必然成功。

本轮使用官方 Mihomo v1.19.33 建立隔离实例：仅一个已保存的节点；关闭 TUN 与嗅探；不加载任何覆写；仅绑定回环入站；明确指定物理出站接口；客户端配置只读。目标 TLS 仍正常校验，不使用 `-k` / `skip-cert-verify` 绕过目标证书。

| 实验 | 1.1.1.1，通常 TLS | 1.1.1.1，指定域名 SNI | www.cloudflare.com | chatgpt.com trace |
|---|---|---|---|---|
| 首轮台湾 VLESS 节点 | TLS EOF | TLS EOF | 200 / TW / TPE | 200 / TW / TPE |
| 首轮另一香港 Hysteria2 节点 | 200 | 200 | 200 / HK / HKG | 200 / HK / HKG |
| 续做时台湾 VLESS 节点 | TLS EOF | TLS EOF | 200 / TW / TPE | 200 / TW / TPE |

首轮证据是 `selected-egress.json` / `control-egress.json`。续做证据是 `selected-egress-recheck.json` / `control-egress-recheck.json`：此时两个保存的策略组已指向同一节点，因此后一个文件**不是独立对照**，不得当作第二次香港测试。两轮配置指纹和节点指纹不同；每次隔离实验期间源配置均逐字节未变，但不能声称整个会话期间用户客户端从未自行更新。

**可支持的判断**：不加载覆写仍可复现，故该故障不需要覆写脚本才能发生。重点转向所选节点的协议实现、服务端转发、上游到该目的地址的路径；没有服务端日志时，不能继续断言是哪一段主动关闭。公开 IP 信誉、地区识别与这个传输错误不是同一证据。

未增加 `1.1.1.1/32` 特例，未关闭全局 IPv6、DNS 防护、TUN、TLS 校验。规则模型与原生回放分别确认：IP 字面量走“漏网之鱼”，Cloudflare 业务域名走“公共基础服务”，ChatGPT 走“OpenAI 服务”。三组可以选择同一节点，但不应因此混淆规则语义。

`one.one.one.one` 作为普通应用目标仍受现有外部 DoH 域名保护；不要为了检测页面而全域放开。指定 SNI 的隔离探针仅用于比较握手路径，不代表生产分流规则的行为。

## 二、已落实的缺陷修复

| 编号 | 缺陷 / 反例 | 修复位置与结果 |
|---|---|---|
| A01 | Android 在 auto / dual-stack 中将 API 域名排除 Fake-IP，却缺少桌面端已有的精确 DoH/443 策略 | `runtime/platforms/android/main.js.in` 补齐同一 OpenAI 策略组的 DoH；不改 ipv4-local / ipv4-only 的 Fake-IP 合同 |
| A02 | 原始 Android 订阅没有 tun 对象时，ipv4-local 对其写字段而抛异常 | `tools/ipv4-local-adapter.js` 创建必要策略对象，但不自动启用 VPN 或接管宿主文件描述符 |
| A03 | 用户规则集与生成的 private 分类器同名时，硬编码名称指向错误对象，且清理过程删除用户嗅探排除项 | 用生成标记查找实际分类器名，保留用户原条目 |
| A04 | auto / ipv4-local / dual-stack 切换遗留生成的排除项，后续生成把自己的分类器当成用户依赖 | 记录排除项所有权，所有模式生成前只撤销本脚本上次添加的项目；补模式往返和幂等测试 |
| A05 | ipv4-lan-dns 仅做外形正则校验，接受非法 IPv4、0 或超范围端口 | 校验每段 0–255、地址文本和端口 1–65535，保留合法 UDP/TCP IPv4 DNS |
| A06 | 旧诊断工具把纯 IPv4 配置被 App 恢复顶层 ipv6=true 的情况误记为通过 | 增加纯 IPv4 核心、节点/provider 地址族、IPv6 拒绝规则、API DoH 策略与组重命名诊断 |
| A07 | 只读本机控制器诊断默认可跟随 HTTP 重定向，破坏“仅回环访问”的边界 | 禁止所有控制器重定向；本地 302 反例确认不请求新目标，不转发认证头 |

修复前新增矩阵为 97 通过 / 63 失败，修复后个人版、公开版均 160 / 160 通过。63 是测试失败数，不是 63 个独立 Bug。

补充告警：监听于非回环且无密钥的控制器列为合同错误；局域网无鉴权代理、非回环 DNS 监听、订阅节点关闭 TLS 校验列为需审核的安全告警。不擅自改掉用户的 LAN 功能，也不假设订阅提供方给出的证书参数一定可直接改动。

## 三、架构取舍及上游核查

保留共享业务源码 → 客户端适配 → 三种网络模式 → 自包含导入文件的构建方式；纯 IPv4 仍是独立产品变体。没有增加常驻服务或运行时 npm 依赖，未引入浮动规则源。

| 主题 | 核查依据 | 本轮取舍 |
|---|---|---|
| DNS 按策略组与引导解析分离 | Mihomo DNS 官方文档 | 保留业务组绑定与独立节点引导，补 Android 精确策略；不全局打开 respect-rules 造成引导循环 |
| 嗅探排除与目标重解析 | Mihomo sniffer 官方文档 | 修复所有权与命名冲突，不全局关嗅探、不从共享 CDN IP 猜域名 |

| Android VPN 接管 | Android VpnService 官方文档 | VPN socket 保护和宿主接管必须由 App 实现；Windows 核心加载不能冒充 Android 实机 |

## 六、使用建议与资源结论

先阅读 [手动部署与验证](../../guides/本轮修复手动部署.md)。不要盲目把主版默认 auto 导入普通核心并假定自动生效；保留此前明确采用的网络模式，纯 IPv4 则核对 App 合并后的顶层标志和系统接管。

没有新增常驻开销。新增逻辑仅在配置生成/诊断时执行；仍通过既有 JS 与生成配置体积预算。没有做可靠的带宽、CPU、电量或长时间内存 A/B，因此不宣称“网速提升 X%”或“资源下降 X%”。主要收益是消除可复现错误、避免用户配置被误删、减少误判和使验收可重复。

包内包含可直接导入的脚本、对应可读源码、固定规则、测试、文档和本轮证据；不包含真实订阅、节点凭据、运行中控制器密钥、HAR 原文、可执行核心或临时 TLS 私钥。个人版不得当公开版发布。
