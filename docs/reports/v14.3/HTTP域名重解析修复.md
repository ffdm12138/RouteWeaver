# HTTP 域名重解析修复

2026-10-16，`http-recovery-r1` / `v14.3.0-rc.4`，追加到 `ipv6-fallback-r2`。本次只补五种 IPv4-local JS 的通用 HTTP 目标恢复，不增加微信规则，不改变标准入口、业务组、未知 UDP 防护或节点选择。

## rc.3 实机结果

用户再次反馈 Windows 图片仍失败。新日志为 17:18:43–17:19:48 的 5,000 行，SHA256 `863c28b37d51562e06f4582ba3e53bef3f3ac810081493d38bcf7a3fa74e24b0`。只读核对确认活动订阅绑定的脚本与当时本地 rc.3 兼容源码逐字节相同；最终配置有 `networkMode=ipv4-local`、`networkCompatibilityRevision=ipv6-fallback-r2`，业务 DNS 三种过滤已在，TLS/QUIC 目标覆盖为 true，HTTP 为 false。没有 rc.2 的宽泛 IPv6 REJECT。物理 Wi-Fi 只有 IPv6 链路本地地址，默认 IPv6 路由由 TUN 接管；两者都不能提供公网 IPv6 出口。

日志有 1,323 条 IPv6 DIRECT 网络不可达警告，按源端口、目标地址和目标端口去重为 134 组连接元组，不能把重试条数当作独立用户请求数。端口分别为 80：1,183 条，8080：10 条，443：70 条，8000：60 条。70 组元组命中国内域名规则，64 组只命中 CN IP 规则。另有 53 条嗅探失败、19 条多次失败后跳过的调试记录，以及一条其它公司业务的节点连接 deadline；后者不能解释全部媒体故障。

这些记录足以否定“rc.3 已解决当前媒体案例”。导出日志没有历史进程 ID，也不含原始 HTTP Host 数据，不能把全部连接归为微信，不能断言每个 IPv6 目标都存在可用 A 记录，更不能据域名规则命中宣称所有失败都能由 HTTP 修复。原始日志、节点和订阅只保存在私人诊断目录，不进入 Git 或 Release。

## 原因与修复

Mihomo 识别域名用于规则匹配，与使用域名重新建立目标连接，是两种行为。rc.3 的 HTTP `override-destination=false` 可以设置嗅探名称，但不会清除已有目的 IPv6；即使因此命中国内域名组，DIRECT 仍可能拨原 IPv6 并报网络不可达。只过滤 DNS 无法更改这条已有字面量连接。

rc.4 在兼容 JS 的既有 HTTP 端口 80、8080–8880 启用 `override-destination=true`，与既有 TLS/QUIC 恢复一致。可读 Host 转为目标域名后再按原 DNS/分流建立连接；有 A 的 DIRECT 可使用 IPv4，公司代理仍经原业务组。最高优先级显式 IP 前缀、完整已审核 private 域名表和用户排除项继续跳过嗅探。没有全 CN UDP 放行，没有强制切节点，没有把 DIRECT 失败偷偷改为代理。

兼容入口会对可读 Host 的 IPv4 字面量也重新解析，可能改变应用刻意选定的具体服务器；必须在模式说明中披露。标准双栈入口和 Shadowrocket 配置保持原字节。新兼容输出标记 `networkCompatibilityRepair=http-recovery-r1`，用于确认实际导入版本。

## 验证

- 修改前的实际 rc.3 代码，在自有回环服务中复现：带有效 HTTP Host 的 IPv6 字面量连接失败；仅将 HTTP 目标覆盖改为 true 后同一请求成功。沙箱内初次实验仅因回环 API 不可访问失败，单独保留，不计入协议反例。
- 当前源码有 51 项兼容静态检查、123 项 Mihomo v1.19.31 隔离核心检查，个人版和公开版分别运行。新增完整自有 HTTP 请求/200 响应、A 记录和 IPv4 服务到达、公司 Host 经 IPv4 节点代理、LAN Host 保持原地址、显式 IP 与公司 Host 冲突、用户 skip-domain，以及只关闭 HTTP 目标覆盖的失败对照。
- 实验保持生产规则，DNS 端点替换为自有回环并固定实验 DNS 传输，所有拨号绑定回环网卡；HTTP/TLS/QUIC 嗅探列表额外加入自有临时端口。没有实际节点、系统 TUN、真实微信会话或公网 IPv6。TLS/QUIC 仍为合成首包和回执，不是完整加密会话。
- 六份标准入口、Shadowrocket 兼容入口和固定外部来源未改变；已有标准业务、Mac、有效空表及冷下载核心回执按实际源码哈希继续核对，不冒充本次重新运行。受影响兼容实验、当前静态合同、个人差异检查和发布包全新解压回放重新执行。公开双平台 CI 与附件下载验收另见对应发布回执。

一次公开版隔离复验遇到测试 UDP 端口已占用，已保留失败回执与核心日志；这不是 HTTP 协议或用户客户端失败。测试工具改为同时探测 TCP/UDP 端口，并等待本轮 TCP/UDP/DNS 监听及规则表真正就绪；最终两份源码依次重新运行并通过。

## 未解决与交付边界

**rc.2、rc.3 的 Windows 媒体案例均失败；rc.4 只证明上述 HTTP 缺口已在隔离核心修复，媒体设备复测仍待做。** 53 条嗅探失败和 19 条跳过记录说明现场还有不能依赖通用域名恢复的路径；本次不宣称它们已解决。

无可用域名/映射的 IPv6 私有协议、缓存字面量、纯 IPv6 DIRECT 服务或显式 IPv6 hosts，无法靠 JS 推导等价 IPv4。原组选择 DIRECT 时仍需真实本地 IPv6 或应用自己的 IPv4 重试。让这类 IPv6 改走代理会改变用户的出口选择，必须另有明确选择并验证节点能力；本版不静默引入。提供真实 IPv6 出口、应用改用 IPv4，或另行授权相应 IPv6 代理策略，属于不同的后续方案。静态覆写没有自动物理网络探测。

本次没有替换运行客户端、重启 TUN、切节点或改系统网络。Android、macOS、iOS、Shadowrocket、公网双栈与网络切换继续各自验收。当前能力见[兼容模式指南](../../guides/IPv4兼容模式.md)与[总报告](IPv6回退与兼容入口.md)。

依据：[Mihomo 嗅探配置](https://wiki.metacubex.one/config/sniff/)、固定 [v1.19.31 replaceDomain 实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/component/sniffer/dispatcher.go)。
