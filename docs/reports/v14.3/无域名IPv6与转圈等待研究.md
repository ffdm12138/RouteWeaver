# 无域名 IPv6 与转圈等待研究

2026-10-16，基于 rc.4 后续 Windows 日志及用户澄清。用户现在能够发送图片，主要现象是发送时转圈等待，不能据此认定上传带宽下降。**当前为部分改善，根因尚未全部闭合；rc.4 导入文件没有包含本报告的核心原型。**

## 兼容链中仍存在的等待

固定上游 Mihomo `ab405bad5beeeac8b003bb01f60f134f6df54471` 的隧道重试器最多调用拨号 10 次，并执行退避。其提前停止条件没有包含本次 DIRECT IPv6 的系统网络不可达。只过滤 AAAA 或恢复部分 HTTP Host 不会消除其余字面量连接的重复拨号；已有日志的 10 次记录与这条机制一致，仍不能单独证明该核心与用户内置核心逐字节相同。

嗅探本身还有独立等待：该上游版本在等首字节、继续读取不足数据时使用时间预算。自有“服务端先发送”连接开启 HTTP 嗅探后，原版/候选均约等待 1.08 秒才收到响应；关闭嗅探对照更快。这证明这类协议可以产生等待，**不证明微信的失败连接一定是服务端先发，也不证明所有 `sniff failed` 都等待一秒**。直接全关嗅探会损失公司识别及现有 IPv4 恢复，不能当作符合当前合同的通用修复。

## 已实现并验证的核心原型

仅在原生 `type: direct` 的 TCP 拨号返回原生网络不可达时，确认真正使用的是无 Host 覆盖的 IPv6 字面量，再标记该错误，让本次隧道重试停止。Windows 使用 Winsock `WSAENETUNREACH=10051`；不能只比较 Go 的 Windows 伪 `ENETUNREACH`，也不能匹配错误字符串。原系统错误保留，新连接重新拨号，没有全局失败缓存。

IPv4、IPv4 映射地址、有 Host 的解析、COMPATIBLE、代理传输的 INNER 元数据、代理错误、超时和 UDP 均不套用这条快速失败；不改分流、节点或目标，不将 DIRECT 偷偷改为代理，也不将代理失败改成 DIRECT。局域网和代理远端 IPv6 继续保留。

| 文档 IPv6 地址原生不可达，5 次独立样本的尝试数 | 每次 10 | 每次 1 |

| 可达回环 IPv4、IPv6 | 成功 | 成功 |

上述耗时只测失败反馈，**不是传输速度，也不是微信回退用时**。实验所有出站绑定自有回环接口，目标为文档前缀，没有启用 TUN、真实节点或公网 IPv6。只在子进程设置跳过上游“存在 IPv6 地址”的粗略检查，以便稳定覆盖原生错误；没有改系统或用户客户端。

最终候选另通过 5 个 Go 测试函数、24 个子例，以及现有 123 项 DNS/TCP/UDP/HTTP/TLS/QUIC/原分流隔离回放。补丁从固定源重新应用后，1,052 个源码文件与受测候选逐字节一致，`go.mod` / `go.sum` 未变；Git 换行转换的首次失败、代理失败夹具的首次错误及较宽原型均单独保留，不作为最终验收。研究代码、许可、重建方式和回执见[核心研究目录](../../../releases/v14.3/research/ipv6-direct-fast-fail/README.md)，公开仓库也可在 [研究目录](https://github.com/ffdm12138/RouteWeaver/tree/main/releases/v14.3/research/ipv6-direct-fast-fail)查看。没有分发核心二进制。

## 保持分流与防泄漏时的完整实现边界

1. **已能识别域名**：继续使用现有 DNS 和域名恢复，按原业务组解析和出站。IPv4 节点传输与节点访问 IPv6 目标独立，不能全局关闭核心 IPv6。
2. **无域名、原策略 DIRECT、路由确实不可达**：核心及时结束失败；客户端还需分别验证系统/gVisor/NetworkExtension 的错误反馈和应用 IPv4 重试。快速失败只能让有后备的应用更早尝试，不能保证应用存在或选择后备。
3. **自动网络适配**：应由客户端/核心跟踪物理连接与有效出口、路由变化，使用有时限的实际可达性证据。TUN/ULA 地址存在不等于公网可达；也不能把确实提供 IPv6 的受控隧道一概排除。网络切换要使旧状态失效，不能因一次目标失败永久禁用 IPv6。静态 JS 无此持续探测能力。
4. **没有域名/可靠映射，也没有应用 IPv4 后备**：保持 DIRECT 语义时，需要真实 IPv6 出口，例如明确配置且验证过的 IPv6-over-IPv4 通道。另一种出口是用户主动把原业务组改选有 IPv6 能力的代理，须单独验证并明确出口变化；现有默认 DIRECT 不会自动这样改。PTR、共享 CDN IP 历史及任意 IPv6 截取都不能提供可靠等价目标。
5. **UDP 和其它协议**：UDP socket 建立成功不等于后续发送成功，ICMP/写入错误到应用的传递另需实现和验收；本 TCP 补丁不冒充解决它们。未知公网 UDP、通用 STUN、CN IP 仅 TCP 捷径和代理故障保护继续成立。

因此当前结论是：rc.4 域名恢复已被现场使用，剩余无域名 IPv6 有可复现的重复拨号等待；核心快速失败方向已完成有界原型。完整的跨应用无本地 IPv6 回退，仍需要客户端集成、错误反馈与实机验证。六个标准、六个兼容入口及已发布 rc.4 标签/附件保持原字节，原型没有自动安装。
