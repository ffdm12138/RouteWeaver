# V14.2 收尾雷霆审核

日期：2026-10-10。当前修订：`review-fixes-r1`、`domestic-selector-r1`、`api-real-ip-r1`。

源码、隔离核心及交付包分别验收。API 的 IPv6 Fake-IP 本地地址检查已有针对性修补，源码和隔离核心通过；用户 Chrome/TUN 的修补后复测尚未执行，当前仍为候选。用户自行切回的 V14.1 保持原状，审核没有替换客户端。

## API 浏览器回归

用户确认：Windows、同一组、同一节点，V14.2 检测失败，切回 V14.1 恢复。此前 DNS/UDP smoke 正常属于用户实测反馈，不能替代本次 API 回归或全部设备验收。

新控制台截图显示三条相关记录：API 根路径 HTTP 421、请求从 `public` 地址空间进入 `local` 被浏览器检查阻止，以及 `net::ERR_FAILED`。脚本第 66 行只是转交原生 `fetch`；第 538 行以 `no-cors`、6 秒超时访问 API 根路径，异常统一显示「不可访问」，没有区分 HTTP 状态、超时和浏览器地址空间拦截。

只读读取实际配置和公开域名解析，观察到 API 的 A 为 `198.18.0.0/16` Fake-IP，AAAA 为 `fdfe:dcba:9876::/64`。Chromium 的地址空间分类将 `fc00::/7` 归为 `local`，IPv4 `198.18.0.0/16` 不在其本地地址列表中。这与截图中的 `public → local` 错误相符。两版脚本均使用该 IPv6 Fake-IP 范围，所以该兼容性触发条件已经确认，两版在当次浏览器连接、缓存或地址选择上的差异尚未单独隔离。[Chrome LNA 说明](https://developer.chrome.com/blog/local-network-access)；[Chromium 分类实现](https://raw.githubusercontent.com/chromium/chromium/main/services/network/public/cpp/ip_address_space_util.cc)。

修补只给 Windows、Android 的 Fake-IP 排除表增加精确 `api.openai.com`，让它返回真实 A/AAAA。IPv6、DNS 传输、公司规则、UDP 拒绝、TUN 和公共组选择不变；DNS 仍按「OpenAI 服务」所选组查询。真实地址解析不表示 DIRECT。iOS 不使用这套 Mihomo Fake-IP 字段，原生配置没有套用此项改动。[Mihomo Fake-IP 和 DNS policy 说明](https://wiki.metacubex.one/config/dns/)。

验证包含保留的修补前源文件、全部生成差异、修改前 Fake-IP 反例，以及修改后两公共组／手动 DIRECT 的 A/AAAA 和断节点拒绝。原生 Fake-IP 模式下修改前 AAAA 返回 ULA，修改后返回本机测试解析器的公网地址；死节点时没有其他上游查询，手动选节点未改变。

另外用当前同一选定真实节点启动自有隔离核心，关闭 TUN、绑定物理网卡，只把远程规则替换为隔离占位表，保留嵌入式 OpenAI 公司规则。当前源码真实 A/AAAA 都为公网地址、不是 Fake-IP；无密钥 `/v1/models` 返回 HTTP 401，根路径返回 HTTP 421。这证明该隔离条件下 API 传输可达，不能代替原客户端的 TUN 和 Chrome 检测。节点的 DoT 853 在独立实验中也成功，不能把本次错误归因于节点封禁 853。

初次未绑定物理接口的隔离实验两种 DNS 传输均失败；完整旧脚本隔离实验也有超时，同时运行中的 V14.1 返回 401。这些负面结果完整保留，不据此推翻用户的 V14.1 实测。内置浏览器曾出现 `ERR_BLOCKED_BY_CLIENT`，其结果不作为用户 Chrome 的等价验收。未调整 Chrome 的安全开关或插件设置。

Chrome/TUN 最终复测应在用户导入候选、由客户端重新加载并清理旧 DNS/Fake-IP 缓存后进行：确认 API 远程地址真实且不再出现本地地址空间错误，再复测节点断开。当前状态为 `API_REAL_IP_CORE_PASS_BROWSER_TUN_RETEST_PENDING`。

## 检测页提示的核实

`api.openai.com` 是 OpenAI API 的入口，网页和 API 的可达性可以不同。但这张卡片只发起根路径的跨域探测，不能证明账户权限、模型调用、Codex 的全部认证和请求链路都可用。官方 Codex 支持 ChatGPT 登录及 API key 等认证路径，应按实际登录方式判断。[Codex 认证说明](https://learn.chatgpt.com/docs/auth)。

「Codex/API 走 Azure 独立基础设施」不能作为一概而论的结论。官方 SDK 明确区分 OpenAI 和 Azure OpenAI 客户端，Azure 接口有独立 endpoint；这既不能证明 `api.openai.com` 必然走某条 Azure 链路，也不能证明 OpenAI 内部没有使用 Azure。[官方 SDK 的 Azure OpenAI 用法](https://developers.openai.com/api/reference/python)。

「服务器通常在美国，所以延迟超过 100ms 正常」只能粗略参考。此检测值还包含客户端、节点、DNS、连接和边缘服务的影响，不是模型推理延迟；仅凭它不能判断部署地域或配置错误。服务状态的轻微故障标记也没有解释截图中的客户端地址空间拒绝。

## 国内分组及需求增补

按用户要求，三端新增「国内网站」手动组，默认 DIRECT，可以选两个公共组、单节点或 DIRECT。原本地域 DIRECT 的 TCP 入口改为该组：固定 CN 主表 111,595 条、22 项本地补充、`.cn`、CN IPv4/IPv6。Mihomo 共 23 条入口，Shadowrocket 共 22 条；公司、共享基础设施及 LAN／既有手动直连优先级保持。

普通海外业务已选代理时，把国内组也切到代理，可实现普通公网流量全部代理的效果。国内组与「漏网之鱼」选同一公共组，便于保持普通国内 TCP 和未知 DNS/UDP 的同一出口。已有手动 DIRECT 业务、LAN 和明确直连例外仍按原约定；覆盖以审核名单为边界，不宣称穷尽所有国内网站。

未知公网 UDP 和未知 DNS 保留代理兜底。Mihomo 地域代理规则后紧邻同条件 REJECT，国内组选代理后节点故障不会落回直连。两个公共组仍只手动选节点，不增加 DIRECT、测速择优或自动故障切换入口。

第十一条已写入 [最终需求](../../需求.md)，原 1–10 条逐字保留。合同前后哈希及授权记录在 `metadata/domestic-selector-amendment.json`；保留的改动前源文件在 `validation/inputs/domestic-selector-before/`，API 修补前源文件在 `validation/inputs/api-browser-before/`。全部 45 个托管来源及 90 份原始／分类文件保持固定提交和原哈希。
