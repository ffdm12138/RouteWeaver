## 三个反例与修复

| 问题 | 修复与回归 | 结论 |
|---|---|---|
| 公共云第三方租户仍归 Google/Microsoft | 新审阅 32 个公共托管命名空间，移入共享分类；删去公司核心的 7 条重叠泛后缀。保留 7 个原有微软专用主机的精确例外，其子域不继承公司身份。同步三端路由、DNS，并检验公司选 DIRECT、共享组选代理的相反选择 | 三端静态、双脚本实际 TCP/UDP、A/AAAA 出口通过 |
| 共享数组空洞被转换为 `undefined/null` | 单一 JSON 数据同步到两个脚本；逐索引校验稠密数组、字符串与域名格式。Shadowrocket 生成器在 JSON 序列化前校验；故障注入验证空洞、null、空串会拒绝生成且不覆盖已有输出 | 反例、故障注入与生成确定性通过 |
| V11 升级清理删除新设置的全路由 | 清理旧 `inet6-address` 时保留 `route-address = [0.0.0.0/0, ::/0]`。六种旧路由/客户端开关组合检查首次输出、二次幂等、严格路由及开关保留 | 反例由失败变通过；未接管 TUN |

例如 `tenant.cloudapp.net`、`tenant.azure-api.net`、`us-central1-thirdparty.cloudfunctions.net` 原先会跟随相应公司 DIRECT；现由「公共基础服务」独立选择。Cloud Storage 的 `storage.googleapis.com`、`storage.cloud.google.com` 等还需要更具体的 DNS 声明，避免被 Google 的宽后缀 DNS 声明抢占。OpenAI 异步 WebPubSub 的有界正则继续先于共享分类。

Azure 租户命名依据来自 [Azure 域名表](https://learn.microsoft.com/en-us/azure/security/fundamentals/azure-domains)、[存储帐户端点](https://learn.microsoft.com/en-us/azure/storage/common/storage-account-overview)、[中国云端点](https://learn.microsoft.com/en-us/azure/china/concepts-service-availability)和 [Azure 中国 API Management](https://docs.azure.cn/en-us/api-management/configure-custom-domain)。Google 部分依据 [Cloud Functions 部署端点](https://docs.cloud.google.com/functions/1stgendocs/tutorials/http-1st-gen)和 [Cloud Storage 请求端点](https://docs.cloud.google.com/storage/docs/request-endpoints)。本项目据此判定这些通用租户命名空间属于共享基础设施；这不是全部云产品租户的完备清单。

逐项来源、增加/排除的规则和保留的精确例外见 `data/rules/classification-review.json`。原始公司输入字节及来源哈希不变；当前嵌入的公司/共享核心为 1,911 条。`foo.undefined`、`foo.null` 及类似后缀的恶意拼接名均检查为代理兜底，节点不支持 UDP 时拒绝，不产生隐式 DIRECT。

## 国内默认直连是否便于维护

规则获取采用固定审核提交的聚合主表：Mihomo 的 CN MRS 和 Shadowrocket 的 CN classical 分类都包含 111,595 条域名后缀，解码语义逐项相同；CN IP 表为 9,609 条。45 个当前托管来源全部固定完整提交，本次未更新任何远程 URL 或原始规则字节。运行下载经「高纯净度AI用」；未选节点时可能尚不能下载，需手动选节点并检查核心 `ruleCount`，不会偷偷转 DIRECT。

旧补充名单 Windows 20 项、Android/iOS 150 项，存在重复维护以及两个 Windows 缺口。本次统一维护 `data/rules/domestic-direct.json` 的 22 项，通过 `tools/sync-reviewed-data.cjs` 嵌入独立脚本，iOS 从同一数据生成。保留 20 项已有本地补充，补上 `baidustatic.com`、`didi-labs.com` 的跨端差异；移除 Android 的 128 条重复补充前，逐条证明已固定 CN 主表或 `.cn` 规则覆盖其整段后缀。

这种「固定主表 + 有界补充 + 单一数据源」便于审核和维护。不会自动采集搜索结果或将未确认网站加入直连。更新候选必须保留提交、原字节、分类器和分流差异，审核后才启用。111,595 条代表该快照覆盖量，不证明全部国内网站都已收录；规则缓存未加载时只保证已嵌入的补充和授权例外，不保证离线完整国内覆盖。

国内直连边界仍按需求：已识别公司/共享服务先于地域规则；一般国内 TCP 可以 DIRECT，未知公网 UDP 走兜底或拒绝，公共 DNS 不因 `.cn` 自动直连。Steam、哔哩等已经识别为业务的域名保留业务组选择，补充表里重叠的条目不会改变它们。未确认的新 `.com` 国内站点可能仍走兜底，需作为候选审核后补充。

对旧 Android 150 项及各自子域，三端完成 2,700 次路由和 900 次 DNS 对照。额外观察到既有 LAN 表差异：`miwifi.com` 在 Mihomo 作为局域网名称放行 UDP，Shadowrocket 则走兜底，不支持 UDP 时拒绝。该差异保持原状并记录在 `validation/domestic-audit.json`；本次没有扩大原生 UDP 直连范围，不能声称两套 LAN 表完全相同。首次国内 DNS 仍可能先经兜底；这是 DNS/未知 UDP 防漏合同带来的取舍。

最初受限沙箱连 `127.0.0.1` 也报 EACCES，失败回执保留在 `validation/inputs/repair-attempts/sandbox-ipv4-eacces/`。允许隔离回环后重新运行，IPv4 路由及 DNS 上述用例通过；IPv6 未运行项目没有转为 PASS。

Mihomo 业务 DNS 继续使用加密 DoT 和 `disable-reuse=true`，生产证书校验开启。参数依据 [v1.19.31 DoT 实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/dns/dot.go)，本次实际验证了 AI → 视频 → DIRECT → AI 的持续连接出口。代价为额外 TLS 握手；应用连接和 DNS 答案缓存本身不承诺立即迁移。

路由 DIRECT 使用带标签的本机模拟出口，DNS DIRECT 则连接本机 TLS/HTTPS 服务器。测试不向真实目标转发、不加载真实订阅、不改运行中的客户端。报告只证明对应源码的本机合同和核心行为，未证明真实设备绝对零泄漏。
