## 出口选择

两个公共节点组都为 `select`，只手动选代理节点，不提供 DIRECT、url-test 或 fallback 链。Mihomo 通过 `store-selected` 保留有效的已有选择，默认和空组使用 REJECT；REJECT 放在首位，防止丢失选择时改选另一个节点。订阅刷新删除已选节点后无法保留不存在的节点，刷新后应复查。旧「节点选择」改名后缓存键发生变化，应首次手动选定新组的节点，此配置不能从未提供的客户端运行缓存读取旧选择。

业务组保留 DIRECT，包括 Steam、OpenAI 等。主动直连是用户的出口选择；代理失败和 UDP 不支持时的自动直连不被允许。独立「自动选择」作为既有功能保留，两个公共组及业务组均不引用它。

**R2 重要行为变更（订阅引导）**：旧 `proxy-providers` 的 HTTP 订阅未设置 `proxy`，现在覆写为 `REJECT`，防止以为订阅在代理内、实际直接连接订阅域名。若需要首次下载，应在订阅提供者原始配置中显式选一个**已经存在、不依赖此订阅下载的节点**；确实允许直连该订阅服务器时，可明确设置 `proxy: DIRECT`。未明确配置前订阅更新会失败，不会偷偷走直连。

iOS 两个公共组默认 REJECT，并按节点名称筛选订阅节点；导入后必须手动选一个节点。这样没有可用节点时不会靠 DIRECT 保持连接。其原生空组、失效节点及选择缓存行为仍需设备验收。

「国内网站」默认 DIRECT，可选两个公共组、单节点或 DIRECT。已审核 CN 域名、国内补充和明确声明的 `.cn` 普通 TCP/UDP/DNS 统一跟随此组；公司和共享服务仍优先。CN IPv4/IPv6 地域 IP 捷径仅适用于 TCP，未知 IP-only UDP 仍走「漏网之鱼」。国内组与「漏网之鱼」可选同一公共组；局域网及 `shiyi.click` 仍是显式直连例外。小火箭完整国内 DNS 的原生跟随须独立实机验证。

`thunder-repair-r1` 将国内组首项设为 REJECT，首次默认仍是显式 DIRECT。Mihomo 订阅更新或重载删除当前已选节点时，本机实验确认该组拒绝，不会自动直连；此时手动选择可用节点或 DIRECT。iOS 同样声明首项 REJECT、默认名称 DIRECT，原生选择缓存和失效回退仍待设备验收。各项证据见 [本轮修复报告](../reports/v14.2/雷霆审核修复.md)。

用户同节点对照发现 V14.2 的浏览器 API 检测回归，控制台记录为 `public → local` 地址空间检查失败。Mihomo 入口已对 `api.openai.com` 排除 Fake-IP，返回真实 A/AAAA；其 DNS 和连接继续跟随「OpenAI 服务」，IPv6 保持开启。隔离核心已验证修补及断节点拒绝，Chrome/TUN 复测待验收。当前状态及证据见 [收尾审核](../reports/v14.2/收尾雷霆审核.md)。

导入本次修补后，由客户端重新加载配置并清理 DNS/Fake-IP 缓存，再关闭旧测试页、重新打开检测。浏览器或系统仍缓存旧 `fdfe:…` 时，新脚本无法改写已有缓存。验收时确认 API 的远程地址为真实公网地址，且不再出现截图中的地址空间错误；API 根路径返回 HTTP 421 本身不能判断 API 链路断开，无密钥访问 `/v1/models` 的 HTTP 401 可用来核对连通性。

## 公司与共享服务

Google、Gemini、YouTube 统一使用「谷歌服务」，Microsoft/LinkedIn 使用「微软生态」。已知公司规则先于国内地址和 `.cn` 的宽泛规则。公司规则核心固化在源码中，不会被远程刷新删掉；删除任意远程业务分类器的回归也检查了重要公司主机仍归原组。

Auth0、LiveKit 不明租户、Cloudflare、AWS、Azure 公共托管、Appspot 等多租户域名进入「公共基础服务」。明确的 ChatGPT Voice 主机和有证据的公司专用租户例外归对应业务；Azure 异步例外由三端共用精确表维护，目前仅审阅 eastus 的 1、17、23 号名称，连接和 DNS 同归 OpenAI；其他编号、地区和子域经公共基础服务。该表保留既有审核子集及历史端点记录，不代表这些端点现仍在用。共享服务不能根据发起页面自动继承公司；需要同出口时可给共享组和公司组选同一公共节点组。

本次补充 Azure CloudApp、API Management、存储等命名空间，以及 Cloud Functions、Cloud Storage 的共享端点。已审核专用主机只匹配精确名称，其未确认子域继续共享；公司组选 DIRECT 不会替共享组作决定。范围与来源见 [审核报告](../reports/v14.2/核实与修复.md)。

## DNS 与 UDP

Mihomo 实际业务上游为 `tls://dns.alidns.com:853#业务组&disable-reuse=true` 和 `tls://dot.pub:853#业务组&disable-reuse=true`。DoT 证书验证保持开启。每次上游查询重新拨号当前所选节点，付出额外 TLS 握手开销，DNS 答案仍可缓存。853 端口必须可经节点连接；不可达时 DNS 失败，不改走系统解析器。非业务直连解析使用直连 DoH。

节点引导通过 `https://223.5.5.5/dns-query#DIRECT`、`https://223.6.6.6/dns-query#DIRECT`，这是明确的独立引导例外。局域网名称 localhost、lan、local、localdomain、home.arpa 保留系统 DNS。只有这些本地名称使用 `system`，公共 `.cn` 不再直接指定本地 DNS。

R3 将应用 DNS 拒绝统一到固定审核快照的 127 条 DOMAIN/DOMAIN-SUFFIX，包含 `doh.18bit.cn`、阿里/DNSPod 和 Cloudflare 的已审核解析器。该阻断先于国内默认 DIRECT，Windows/Android 内嵌不依赖规则下载。核心自身引导/上游属独立控制面，业务主动 DIRECT 的相应 DNS 能力保留；任意自定义 DoH、ECH、应用直连及 VPN 外请求仍须设备验证。

已识别的普通国内 UDP 使用「国内网站」，其他已识别 UDP 使用对应业务组；Mihomo 为每条代理匹配紧邻增加同条件 REJECT，防止节点不支持 UDP 后落到 DIRECT。可识别的通用 STUN 端口/名称先于国内域名；未知公网 IP UDP 保护先于地域 IP 直连。私有 IP、私有本地名称和既有手动直连例外属于授权直连。业务主动选择 DIRECT 后，该业务 DNS/UDP 正常直连。

国内普通 TCP/UDP/DNS 跟随「国内网站」，默认 DIRECT，切到代理则三者跟随代理。公司/共享服务、应用 DoH 拒绝及 LAN 例外保持优先；通用 STUN 和未知公网 IP UDP 继续受保护。DNS 不携带后续连接端口，普通 HTTPS 名称/端口中隐藏的 STUN 也无法仅凭这套规则穷尽识别。

国内覆盖使用固定提交的 CN 主表，加统一维护的 22 项本地补充；公司/共享规则仍优先，Steam、哔哩等业务按其组选择。主表下载经「高纯净度AI用」，首次应选节点并检查规则已加载；下载失败不自动改走 DIRECT。两脚本与原生 CN 域名表语义一致；R3 统一精确 LAN 域名范围，包括 `miwifi.com`，精确路由器主机不扩大为整个后缀。

## Windows

### FlClash 0.9.0 的 TUN 与 DNS 设置

**开启 TUN，并在「设置 → 网络 → TUN」开启「严格路由」；「追加系统 DNS」保持关闭。** 在核心使用规则模式，保留 IPv6。重新连接 TUN 后再做 DNS 检测。

Windows 脚本一直生成 `strict-route: true`，合并 UDP/TCP 53 劫持并设置 IPv4/IPv6 全路由，移除地址/地址集合层面的旁路；TUN 的 `enable` 和 `auto-route` 保留客户端控制。FlClash 0.9.0 新增应用层「严格路由」，默认关闭。应用在脚本执行后再合并网络设置，并能把此值实时写入核心，所以脚本中的开启值不能代替应用开关。依据为 [0.9.0 发布记录](https://github.com/chen08209/FlClash/releases/tag/v0.9.0)、固定提交的 [最终配置合并](https://github.com/chen08209/FlClash/blob/03f955382409a4a7ac1f3f92e46d9fcc6d39f106/lib/common/task.dart)、[TUN 默认值与实时更新参数](https://github.com/chen08209/FlClash/blob/03f955382409a4a7ac1f3f92e46d9fcc6d39f106/lib/models/clash_config.dart)及 [核心 TUN 更新](https://github.com/chen08209/FlClash/blob/03f955382409a4a7ac1f3f92e46d9fcc6d39f106/core/config.go)。

Mihomo 在 Windows 上通过严格路由添加防火墙规则，阻止多网卡 DNS 绕出；它在 TUN 自动路由启用时发挥作用。[官方说明](https://wiki.metacubex.one/config/inbound/tun/#strict-route)

0.9.0 取消了旧的 DNS 总覆写开关，改为全局 DNS 页面中已选择的字段应用到订阅。若 DNS 仍异常，检查全局 DNS 是否额外覆写了 `nameserver`、IPv6 或 Fake-IP 等字段；要沿用脚本对应字段，应移除那一项全局覆写，而不是关闭核心 DNS。完整业务 DNS 与固定来源仍由脚本生成；不要添加面向未知公共域名的系统 DNS 回退。

局域网直连由核心规则决定；脚本不会在 TUN 之前排除整个 ULA，避免 IPv6 Fake-IP 和应代理域名绕过规则。还应检查应用中的「绕过私有路由地址」及「排除路由地址」，它们也是应用层设置，可能使部分目标在到达核心规则之前绕过 TUN。V11 升级只清理旧版强制的特定 IPv6 接口地址；双栈全路由和客户端开关保留，六种合成升级组合已验证幂等。

**2026-10-14 用户复测记录**：用户在 Windows FlClash 0.9.0、TUN 模式下按本轮开关建议调整后，反馈 DNS 检测不再泄露。本次无需修改 JS。这是该用户环境的复测反馈；检测站、解析器地址、抓包和多网卡组合未提供，不将其扩大为所有 Windows 场景或全部 DNS/UDP/IPv6 设备验收通过。

### 切换系统代理模式

同一份 [Windows v14.3.js](../../releases/v14.3/src/windows/v14.3.js) 可以直接沿用，无需另一份脚本或修改 DNS 表。关闭 TUN、开启「系统代理」，运行模式保持「规则」；两个公共组和各业务组仍按原来的方式手动选出口。再次开启 TUN 时，继续保留「严格路由」开启及「追加系统 DNS」关闭。

TUN 与系统代理是接管方式；「规则 / 全局 / 直连」是核心运行模式。切换接管方式不需要切成「全局」或「直连」，这两个运行模式会改变本项目的规则分流。

| 项目 | TUN 开启且应用路由正确 | 仅系统代理 |
|---|---|---|
| 进入核心的公司/国内分组与手动出口 | 使用当前脚本 | 使用同一脚本 |
| 进入核心 DNS 的查询 | 使用脚本 DNS 策略 | 使用同一 DNS 策略 |
| 应用和系统自行发出的 DNS | 由 TUN 劫持及严格路由保护，并需实机核对 | 不因打开系统代理就自动接管 |
| QUIC、WebRTC、游戏等 UDP | 纳入 TUN 的流量由 UDP 规则处理 | Windows 系统代理不自动接管；应用须显式使用支持 UDP 的代理 |
| 不遵守系统代理的应用及 IPv6 连接 | 纳入 TUN 的流量按规则处理 | 可以直接联网，脚本无法处理未进入核心的连接 |
| `strict-route` | 参与 Windows TUN 防漏 | TUN 关闭后不提供这项保护 |

Windows 系统代理由 FlClash 指向本地混合 HTTP/SOCKS 端口；只对实际使用该代理的应用生效。HTTP CONNECT 或将域名交给 SOCKS5 的连接可在核心内解析并按业务组发送 DNS；应用若先在本地解析、忽略系统代理或自行走其他 DNS 路径，相关 DNS 不会自动进入脚本。仅系统代理也不能保证 WebRTC、应用自有 DNS 或全部 IPv6 被接管。需要全系统防漏时保留 TUN，并检查浏览器、系统 DNS 与多网卡行为。

检查「设置 → 网络 → 绕过域名」。该列表在应用连接本地代理之前生效，匹配的目标不会经过脚本。0.9.0 上游默认值包含部分公网域名，例如知乎、京东；若希望这些网站也由「国内网站」组控制，应移除相应公网绕过项，本机/局域网项按需要保留。依据为固定提交的 [系统代理状态](https://github.com/chen08209/FlClash/blob/03f955382409a4a7ac1f3f92e46d9fcc6d39f106/lib/providers/state/proxies.dart)和 [默认绕过列表](https://github.com/chen08209/FlClash/blob/03f955382409a4a7ac1f3f92e46d9fcc6d39f106/lib/models/config.dart)。

本轮用合成节点分别生成 TUN 开启/关闭配置，确认开关由输入保留，两种配置的 DNS、规则、策略组、规则提供者、IPv6 和混合端口一致，关闭 TUN 的重复覆写仍幂等。这是配置检查；系统代理下的浏览器、真实 DNS 和 UDP 仍需实际应用核对。切换后重新打开目标页面，并在连接列表确认公司组和所选出口。

本版保留 IPv6 字面量节点，不强制全体节点 IPv4。新订阅中用户明确设置的节点 `ip-version` 保留。到节点的地址族与远端节点到目标的地址族是两段独立连接；远端出口仍由节点协议和服务器决定。

## Android

核心 IPv6 和 DNS IPv6 开启，保留应用管理的 TUN/VpnService 参数。还须在客户端开启 IPv6、DNS 劫持，让浏览器和目标应用纳入 VPN，并关闭允许绕过。私人 DNS、浏览器安全 DNS、应用排除列表、其他 Android 用户和 VpnService 建立的 IPv6 路由需要在手机检查；JavaScript 无法修改这些系统状态。

本机用 Android 脚本生成的配置执行了 Mihomo 实际解析、路由和 DNS 测试，它不等同于 Android 手机验收。

## iOS Shadowrocket 候选配置

导入节点后再导入配置，全局路由使用「配置」。保留原生规则、IPv6、`:53` DNS 劫持、`udp-policy-not-supported-behaviour = REJECT`，允许 QUIC 经所选节点。共享服务与公司优先级按相同合同生成。

业务 DNS 用 `[Host] server:DoH#proxy=URL编码组名` 声明，开启 `use-local-host-item-for-proxy`，缺省 DNS 经漏网之鱼，系统 DNS 回退关闭。**Host 与 proxy=策略组的组合、切换后的 DNS 连接复用、原生 TCP/UDP/IPv6 和失效节点尚未在 Shadowrocket 实机验证，不能据静态测试声明已满足严格 DNS 跟随。**

R1 生成器把 14 个本地已审核分类器的 DOMAIN/DOMAIN-SUFFIX 公司域名也纳入 Host DNS，并按连接规则优先级保留共享父域和精确租户。R2 进一步将 Netflix/Disney/Epic Games 混合远程表收窄为审核过的域名投影，Netflix/Telegram/Twitter IP 使用与 Mihomo 审核输入一致的 no-resolve CIDR，移除可能跨租户的泛关键词、User-Agent、ASN。部分 Mihomo 原有 DOMAIN-REGEX 未作不安全的宽泛移植，相应未识别流量走代理兜底。R3 统一 DoH/private 投影，R4 统一精确 Azure 例外。R5 补齐 118 个 Epic/Disney 精确 CDN 端点：Disney 和 Epic Akamai 的有限数字规则完整展开；腾讯云两类前缀只按 100 个复核精确端点归 Epic，其他同类编号/前导零/可疑名称三端均归公共基础服务，不扩展整个共享云的公司归属。10,636 个有限域名样本零业务 DNS/UDP 错配、零分组差异；当前端点在线/归属未外部核实，Shadowrocket 原生未验收。

Mihomo 的 `disable-reuse` 参数没有移植给 Shadowrocket。原生宽泛 Azure 通配符在 R3 删除；R4 的三个已审核精确例外同步恢复 OpenAI 连接和 Host DNS，其他租户保持共享出口。R5 的通用 STUN TCP 标准端口和可识别 stun/turn 主机名保护先于国内分组，同时保留已知业务与 LAN 优先。隐藏在普通国内 HTTPS 主机/端口且不可识别的 STUN 不作内容层穷尽防护。该端在原生验收前保持候选状态。

历史 R6 记录了 52 个单标签名称的跨端例外，Mihomo 按已审核 private 正则本地直连，Shadowrocket 未移植这个正则。当时 Shadowrocket UDP 走兜底；本轮已审核国内名称的普通 UDP 改为跟国内组。原历史结论见 [R6 收尾审核](../reports/v14.2/收尾雷霆大审核R6.md)，当前行为与实机边界见 [本轮报告](../reports/v14.3/国内协议跟组与小火箭精简.md)。

## 设备验收

分别测试公司 TCP、QUIC/Voice/WebRTC UDP、A/AAAA DNS，观察连接链和 VPN 外抓包；依次选 AI 组、视频组、单节点、DIRECT，再切回代理。对不支持 UDP 和失效节点检查拒绝、未换节点、未直连。IPv4/IPv6 均需真实目标、真实节点拨号及直连检查。DNS 测试站显示递归解析器位置不直接证明出口，应结合节点连接和外侧抓包。


R3 自定义入站检查：HTTP/SOCKS 等普通 listener 保留并使用主规则；带 `proxy` 或 `rule` 的 listener、额外 TUN listener、指定独立出口的 tunnel 会明确报错。请在原始配置中移除这些旁路字段或为独立配置单独审核；脚本不会静默继承，也不自动修改已运行客户端。

2026-10-16 后续状态：rc.2 与 rc.3 的 Windows 媒体实测均失败；rc.4 补齐可读 HTTP Host 的目标重解析，仍不保证无域名 IPv6 DIRECT 可用。核对兼容标记 `networkCompatibilityRepair=http-recovery-r1` 和最终 HTTP 目标覆盖；[本轮报告](../reports/v14.3/HTTP域名重解析修复.md)区分核心修复与媒体未验收。
