# 策略组故障转移

主版和纯 IPv4 版的六个 Mihomo JS 入口使用原生 `fallback`。导入对应客户端的原文件名即可。规则模式的代理页新增「故障转移1」「故障转移2」「故障转移3」。 [Mihomo 原生回退](https://wiki.metacubex.one/config/proxy-groups/fallback/)

## 怎么选

- 在原业务组直接选 `A ↻`。从未带 `↻` 的旧版升级时需要重选一次。三档备用均默认 REJECT，手选节点后启用对应档。
- 新连接按 **A → 1 → 2 → 3** 选择。优先级较高的出口恢复后自动切回。活动链根据最近一次 HTTPS 204 健康结果选路，探测间隔 3 秒，超时 3 秒。
- 切到 REJECT 的档位在下一轮探测后跳过。全挂只尝试 A。订阅移除 A 后走健康的手选备用，全部不可用则拒绝。
- 「漏网之鱼」、公共组和选代理的「国内网站」都参与。主动 DIRECT、REJECT 按原策略执行，「自动选择」独立运行。业务 DNS 走对应业务组的出口，选定出口缺少 UDP 能力时拒绝。
- 节点直接写在订阅的 `proxies` 时可使用三档。由 `proxy-providers` 提供节点的订阅沿用原分流，脚本会提示三档未启用。

已有连接在应用重连后重新选路。小火箭在两轨沿用原配置。 [Shadowrocket 官方版本记录](https://apps.apple.com/us/app/shadowrocket/id932747118)

## 健康检查与切换时序

探测在后台运行。A 健康时，新连接直接用 A，无需等探测结束。故障恰好发生在一次成功探测之后、下一次探测又等满超时时，活动链通常要经历一个探测间隔再加一次超时。3 秒加 3 秒约为 6 秒，空闲链可暂停探测，应用重连也可能增加恢复时间。

5 秒间隔、3 秒超时来自最初的项目方案。Mihomo 允许分别配置这两个参数，官方配置示例为 300 秒与 5000 毫秒。实际配置要权衡故障发现速度与临时拥堵时的误切概率。原生回退按最近结果选路，一次超时就可能暂时降档。 [Mihomo 策略组参数](https://wiki.metacubex.one/config/proxy-groups/)

以下为历史 native-fallback-r3 时序观测，不是本轮手机恢复时间。原装 Windows FlClash 0.9.3 使用回环模拟节点。备用已健康时，测量主节点失效到新 TCP 请求实际走备用的时间。另在主节点业务仍可用时让一次探测延后 2.7 秒。

| 间隔 / 超时 | 注入故障后接管 | 单次慢探测 |
|---|---|---|
| 5 秒 / 3 秒 | 8.23 秒 | 保持主节点 |
| **3 秒 / 3 秒** | **6.12 秒** | **保持主节点** |
| 3 秒 / 2.5 秒 | 6.11 秒 | 短暂切到备用 |

两轨采用 3 秒间隔、3 秒超时。活动期间探测轮次更密，单次慢响应的判定阈值仍为 3 秒。实验数值对应这组回环条件。 [隔离实测记录](../../releases/v14.3/validation/proxy-failover/native-fallback-r3.json)
