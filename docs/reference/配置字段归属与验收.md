# 配置字段归属与验收

这张表描述当前 RouteWeaver 业务合同与客户端集成边界，用于排查“脚本设置了，但最终值不同”。它不是新增客户端支持声明；不同版本必须核对最终运行配置。

| 领域 | 当前职责 | 必须核对的最终结果 |
|---|---|---|
| 公司/国内/兜底规则、规则提供者与组引用 | 共享业务源码生成；平台适配仅处理兼容差异 | 公司优先、两个公共手动组、国内集中选择、未知 UDP/STUN 与失败保护符合需求；不能被后置规则改写 |
| 节点和 provider 的显式参数 | 保留用户输入，只有未指定的域名节点补地址族默认值 | 节点不被换名/换出口，已有 ip-version 和 provider 变换仍有效；同一节点的地址族后备与换节点分开 |
| 业务 DNS 策略与兼容模式过滤 | JS 产生目标设置，App 的 DNS 开关可能二次合并 | nameserver-policy 的出口、内部 AAAA/SVCB/HTTPS 过滤、节点引导与 LAN 解析逐项核对；空 AAAA 不证明所有 IPv6 已回退 |
| 核心 IPv6、TUN 地址/路由、启停与严格路由 | 目标受合同约束，App 负责实际启动和系统接管 | App 合并后的值、实际 IPv4/IPv6 路由及泄漏结果。TUN 地址存在不证明公网可达；不得自动启动/重启用户客户端 |
| HTTP/TLS/QUIC 嗅探与目标重解析 | 兼容 JS 在既有端口启用，App 仍可能覆写 | 每种协议的最终 override 值、排除项、实际核心支持。识别名称和重建目标不同；失败记录不等于固定耗时 |
| 物理出口/路由变化与原生不可达错误 | 需要客户端/核心能力 | 原生 errno、单次连接反馈、新网络状态失效；静态 JS 和 x-v14 标记不能代替持续探测 |
| 当前设备观测 | 单独记录实际日志窗口、版本和源哈希 | 用户报告与受控验收分开；不把 Node/Windows 核心结果当成 JavaScriptCore 或其它平台 VPN 通过 |

排查时保存原始日志的只读快照和 SHA256，脱敏记录活动入口哈希及最终关键值，再按连接元组区分重试。先确认错误发生在本机到节点、节点到目标还是本机直连目标，分别判断 DNS、嗅探等待和拨号退避；没有文件大小/流量/时间证据时不推断带宽。

FlClash 0.9.0 的已审核应用合并边界见[使用说明](../guides/使用说明.md)；当前 IPv6 的实测与局限见[转圈等待研究](../reports/v14.3/无域名IPv6与转圈等待研究.md)。开源比较与可执行的整理顺序见[公开方案比较](../reports/v14.3/公开覆写方案比较与改进取舍.md)。
