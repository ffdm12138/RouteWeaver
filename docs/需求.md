# 覆写脚本最终需求

来源：用户 2026-10-10 最终整理，后续明确授权的补充按日期登记。以下为验收合同，替代旧版本文档中的不一致口径；新增条目的实现和验收状态另行标明，不代表当前发布已实现。

1. **按公司分组**：OpenAI、Anthropic、Google、Microsoft 等各自归组，不串组、不泄露；Gemini、YouTube 统一属于 Google。共享基础设施独立归组，不随意归属某家公司。
2. **DNS 跟随策略组**：业务域名的 DNS 查询经对应业务组所选节点发送，不得非预期本地泄漏；不要求使用节点自带 DNS，节点域名解析允许必要的独立引导 DNS。
3. **UDP 跟随策略组**：包括 QUIC、语音、WebRTC 等；能识别的业务 UDP 跟对应公司组走，节点不支持 UDP 则拒绝，不得偷偷直连。
4. **IPv4/IPv6 双栈正常**：直连和代理连接在相应出口具备能力时均支持双栈，按第 12 条区分本机、节点和目标的地址族；所有应代理流量不得绕过代理，尤其防止 IPv6、DNS 和 UDP 泄漏。
5. **保留 DIRECT 选项**：各业务组允许用户主动选择 DIRECT，包括相应 DNS/UDP；但代理故障、节点失效或协议不支持时不得自动回落直连。
6. **调整公共节点组**：「节点选择」改名「高纯净度AI用」，新增「高网速视频用」。各业务组可跟随两个组，也可选单节点或 DIRECT；两个公共组本身不提供 DIRECT，均为手动选择，不自动测速择优或故障切换，保留用户选择。
7. **统一兜底**：未知 TCP、UDP、DNS 统一归入「漏网之鱼」，只允许代理，不得非预期直连；明确授权的国内和局域网直连除外。
8. **规则优先级**：已知业务优先归对应公司；通用 STUN 防漏先于宽泛国内直连，不能抢占已识别业务。
9. **规则更新安全**：远程更新不得未经审核改变重要分流，尤其代理变 DIRECT、业务错分组和 DNS/UDP 出口不一致；高风险更新需审核后启用。
10. **三端一致性与验收**：Windows FlClash、Android Mihomo、iOS Shadowrocket 尽量保持相同组和语义；验证 TCP、UDP、DNS、IPv4/IPv6、节点故障及切换。TUN/VPN 模式重点防泄漏，系统代理模式明确接管边界。
11. **国内网站集中切换**（用户 2026-10-10 追加，2026-10-13 明确修订）：保留「国内网站」手动组，默认 DIRECT，可跟随「高纯净度AI用」「高网速视频用」、选单节点或主动 DIRECT。当前已审核国内域名主表、22 项补充、关键母域和已声明的 `.cn` 后缀，其普通 TCP、UDP、DNS 统一跟随此组；不再把这些域名的全部 UDP 当作未知流量送去兜底。公司/共享业务、局域网及显式手动例外先行；能识别的通用 STUN/STUNS 主机与标准端口在普通国内域名规则之前保护。仅凭 CN IPv4/IPv6 地域命中的无域名流量仍只放行 TCP；未知公网 IP 的 UDP、未知域名 DNS和可识别的通用 STUN/WebRTC 继续经「漏网之鱼」代理或拒绝。`.cn` 已在审核表和本地合同中明示，属于域名例外；不得把这个例外扩大为所有 CN IP 的 UDP 直连。覆盖以已审核规则为限，不宣称穷尽国内网站或识别隐藏在普通 HTTPS 名称/端口的 STUN。业务及国内组选代理时，代理失效或不支持 UDP 均拒绝，不得回落 DIRECT。DNS 按域名选择，无法按尚未发生的连接端口区分同名普通业务与隐藏 STUN；这个既有上下文边界必须单独说明。Shadowrocket 的原生 DNS 与代理端远端解析仍须实机验收。

12. **本地无 IPv6 出口的兼容与分段地址族**（用户 2026-10-16 追加，**rc.2/rc.3 媒体失败，rc.4 用户可发送但仍转圈，完整回退未完成**）：不能假定本地网络具有可用公网 IPv6。分别处理「本机到节点」「节点到目标」「本机直接到目标」三段能力；本机通过 IPv4 连接节点时，应保留节点访问 IPv6 目标的能力。节点域名优先使用可达地址，保留同一节点的其他可用地址族和用户显式设置；直连的 IPv6 字面量不能仅靠关闭 AAAA 解析或节点拨号偏好转换为 IPv4。具体边界和验收见下方追加说明。

总体原则：按公司归组，按节点组手动选择出口，公司业务和已审核国内域名 DNS/UDP 跟随本组；国内 IP 地域例外仍只接管 TCP。出口具备能力时双栈正常，本地缺少 IPv6 时按第 12 条明确处理，代理失败不意外直连。保留成熟功能，不做无必要重构。上一国内协议合同的原字节留于独立本地归档，不随公开仓库分发。

验证必须分别说明源码合同、本机核心执行、包完整性、实际设备接管。未运行和被环境阻止的项目不得计为通过。正文中的 DIRECT 都区分主动选择、明确国内/局域网例外和禁止的自动回落。

## 2026-10-16 本地 IPv6 出口能力与兼容要求

**状态：`ipv6-fallback-r2` + `http-recovery-r1` / rc.4 已补齐 HTTP Host 目标重解析，51 项兼容静态、123 项隔离核心检查通过。rc.2 与 rc.3 Windows 媒体案例均失败；rc.4 用户已能发图但仍转圈；无域名 IPv6、完整媒体性能和其它平台设备验收仍未完成。** 当前证据和限制见[IPv6 回退与兼容入口](reports/v14.3/IPv6回退与兼容入口.md)。

### 三段能力分别判断

- **本机到代理节点**：节点有 A/AAAA 不等于本机能使用两个地址族。节点域名应支持选择可达的地址；Mihomo JS 的实现默认值为 `ip-version: ipv4-prefer`，只为未明确指定地址族的域名节点补默认值，保留 IPv6 后备。原始节点、provider payload 和后续刷新均应覆盖；已有节点设置、provider 固定覆写及用户自定义表达式的显式选择必须保留。IPv6 字面量节点不能凭空生成 IPv4 地址；本机无法连接时明确报错，不擅自换节点。
- **代理节点到目标**：与上一段独立。本机用 IPv4 连节点，仍可通过支持相应协议和 IPv6 出口的节点访问 IPv6 目标，TCP/UDP 分别验收。节点缺少 IPv6 出口或协议不支持时保留失败证据，不改成 DIRECT；不能把节点可连接当作其远端 IPv6 出口已通过。
- **本机直接到目标**：需要本机真实可用的公网 IPv6 出口。TUN 的 IPv6 地址、默认路由、其他虚拟网卡的 IPv6，或 DNS 返回 AAAA，都不能单独作为可用证明。IPv6 字面量没有可靠的域名或地址映射时，脚本不能替它推导等价 IPv4 目标。

### 兼容模式与既有分流

用户选择保留标准双栈，并另提供手动 IPv4 兼容入口。五种 Mihomo JS 兼容入口向应用返回空 AAAA、移除 IPv6 Fake-IP 池，保留核心 IPv6 和双栈 TUN 接管；业务/直连解析上游同时过滤 AAAA、SVCB 和 HTTPS 记录，避免内部解析或 IPv6 提示继续选择不可用的本地 IPv6。DNS 原策略组、节点引导 DNS、LAN/system 和用户显式 hosts 保留。兼容模式在既有 HTTP/TLS/QUIC 嗅探端口使用可读域名重解析目标；局域网名称及最高优先级显式 IP 例外排除目标重写，已知公司域名优先级保持。IPv4 字面量也可能按 HTTP Host 或 TLS/QUIC 域名重解析，SVCB/HTTPS 过滤对服务发现/ECH 的影响必须明示。

rc.2 前置拒绝公网 IPv6 的方案已被实机媒体失败否定为充分修复，rc.3 撤掉该宽泛拒绝；IPv6 目标按原业务组和手动选择处理，IPv4 节点传输仍可承载远端 IPv6。只有原策略选择 DIRECT 的连接才本地直连，失败不改成代理或其它节点。Shadowrocket 可选 conf 仅提供原生 IPv4 偏好，没有已验证的同等过滤和域名恢复能力，不宣称完成等效回退。无可靠域名映射的私有协议/缓存 IPv6 字面量仍不能推导等价 IPv4；应用及媒体结果必须实机对照确认，不能用空 AAAA、节点偏好或连接拒绝代替验收。

不得为解决「本机到节点」的问题默认关闭所有 IPv6 能力。兼容模式必须明确其影响，联动核对核心、DNS、Fake-IP、TUN 地址/路由和旧连接；网络切换后不得让应代理的公网 IPv6 绕过代理。静态覆写 JS 无法可靠判断操作系统当前出口，自动适配应由具备相应能力的客户端或受控组件承担；未实现自动检测时必须明确采用手动模式。

「国内网站」的手动选择和默认 DIRECT 保持。不得因 DIRECT 的 IPv6 失败就静默转代理；如另设用户明确选择的 IPv6 代理方案，应说明出口变化，并先验证节点能力。不得把 CN IP 的 UDP 例外扩大；未知目标、通用 STUN、节点失效和 UDP 不支持的防护继续成立。保持公共组手动选节点；同一域名节点的地址族后备不等于换节点。

### 新增验收范围

验证本地 IPv4-only、本地可用双栈、同一节点 A/AAAA 的一种地址不可达、AAAA-only/IPv6 字面量节点、IPv4 节点传输承载 IPv6 目标、远端缺少 IPv6 出口、provider 刷新和显式设置保留。TCP、UDP、DNS、微信缓存/字面量地址，以及 Wi-Fi/热点和 TUN/VPN 重连前后的行为分别记录。应用没有可用 IPv4 后备时，应明确剩余限制，不能承诺通过透明地址转换修复。

Windows、Android、macOS、iOS Clash Mi 和 Shadowrocket 按各自原生能力实现和验收，不直接复制不兼容字段。本机隔离回环实验只证明核心和协议行为，不能替代公网 IPv6 出口、微信实测或跨平台 VPN/TUN 验收。

2026-10-16 后续复测：rc.3 已生效但媒体仍失败，HTTP 域名仅用于分流而未重建目的连接是已复现的缺口。rc.4 补齐该通用路径，仍不承诺恢复嗅探失败、无域名或无 A 的 IPv6 DIRECT；此类流量若改走代理必须另有明确选择，不能静默改变出口。详见[HTTP 修复报告](reports/v14.3/HTTP域名重解析修复.md)。

### 2026-10-16 无域名 IPv6 与转圈等待的追加验收项

用户后续澄清为发送时转圈等待，不能将主观现象当作上传带宽下降。当前 rc.4 为部分改善：可以发送，但仍有无域名 IPv6 DIRECT 网络不可达和重复拨号；不是完整回退已通过。

后续客户端/核心应在原策略与目标不变的前提下，及时结束已由系统明确返回网络不可达的字面量 IPv6 DIRECT TCP 拨号，保留原错误，并在新连接/网络变化后重新尝试。不能把超时、IPv4、代理错误或 UDP 写入错误一概归为此条件，不能据此全局停用 IPv6。嗅探等待、TUN/VPN 错误反馈与应用 IPv4 后备分别验收；不通过全关嗅探、固定 CDN IP 推测、前置宽泛拒绝或静默换出口掩盖缺口。

自动能力状态应基于有效出口/路由及有时限的实际可达性证据；TUN 或 ULA 地址本身不足，合法且确实提供 IPv6 的受控隧道不能一概忽略。新网络要使旧状态失效。无域名/可靠映射且应用没有 IPv4 后备时，保留 DIRECT 仍需真实 IPv6 出口；另选代理必须明确由用户选择，并验证节点 IPv6 能力。

上述属于待客户端集成及实机验收的要求。已交付[有界核心原型与证据](reports/v14.3/无域名IPv6与转圈等待研究.md)，不在 rc.4 JS/conf 内，也不宣称替所有协议提供透明地址转换。
